## 基本方針

CURIEは、債券運用の分析・入れ替え提案・発注支援を行う。

- 数値計算、評価、最適化、制約判定はRで行う。
- AI（Claudeエージェント）は、クレジット資料の読解・整理、数値結果の説明、提案理由の文章化を担う。AIは数値を計算・変更しない。
- LagrangeFinance の Part II の関数（`R/z0_utility/lagrange/` に移植）と GaussQuant・QuantLib を利用し、同じ計算を重複実装しない。
- 入力データ、計算条件、出典、結果を追跡できるようにする（ファイル名・市場日・取得時刻・識別子・計算状態を出力に残す）。
- 未確定の計算条件は推測で決めず、未計算として理由を残す。
- 外部システム（Aladdin等）のエンドポイント・項目名・認証は、仕様の提示前に推測で実装しない。

### A2 時価適正性の検証 ［構想］

ICE時価、DIR時価、オファー価格と当社Fair Valueを比較し、指定した閾値を超える乖離を抽出する。

**当社Fair Valueの考え方**：前月のBloomberg時価から逆算した評価パラメータを、当月の市場カーブに
適用して求める。前月価格をそのまま当月のFair Valueとしない。

既存関数で実現できる経路（候補。どれを採用するかは未確定）：

| 候補 | 前月：パラメータの逆算 | 当月：価格への適用 |
|---|---|---|
| ASW | `compute_asset_swap_ISO()` で前月のBloomberg価格・前月のOISカーブからフェアASWを求める | 当月のOISカーブで `compute_asset_swap_ISO(spread_bp = 前月ASW)` とし、`asset_swap_fair_price()` でNPVがゼロとなるクリーン価格を求める |
| Zスプレッド | `GaussQuant::bond_zspread_GQL()` で前月の価格・カーブからZスプレッドを求める | `GaussQuant::bond_npv_with_zspread_GQL()` で当月カーブに同じZスプレッドを加えて評価する |

未確定（実装前に確認する）：

- 逆算するパラメータ（ASW、Zスプレッド、その他）
- 基準カーブ（OIS、国債、その他）と、Zスプレッドの複利・日数計算の規約
- パラメータを銘柄別に持つか、発行体・格付け・年限などの区分で持つか
- 前月のBloomberg時価がない銘柄（新発債など）の扱い
- Bloomberg時価の種類（価格の種別・取得時点）と、前月の評価日・受渡日
- 閾値の単位（価格差か、スプレッド差か）と水準
- ICE・DIR時価の価格の定義（クリーン／ダーティ、評価日・受渡日）

比較時は、価格単位、通貨、クリーン／ダーティ、評価日、受渡日をそろえる。前月Bloombergデータと
当月市場データの出典（ファイル・市場日・取得時刻）を残す。

### A3 クレジットレポート読込・紐づけ ［構想］

- オファー銘柄と証券会社のクレジット・格付けレポートを、ISINまたは発行体IDで関連付ける。
- レポート名、証券会社、公表日、原文URLを保持する。URLがない場合は空欄とし、推測で生成しない。
- 格付け、見通し、信用上の論点を整理する（Claudeエージェントによる読解・要約。参照元と日付を必ず付ける）。
- オファーExcelのオファー行から、対応するレポートを開けるようにする。
- 複数資料がある場合は、別シートに一覧と要約を作る。

未確定：レポートの入手元・形式、発行体IDの体系、レポートの保存・閲覧権限。

### A4 日次レポート・目玉オファー ［構想］

- 当日のクレジットレポートを集約する（A3）。
- 前回との比較で新規オファー・変更オファーを抽出する（A1の結果を比較）。数値差分の判定はRで行う。
- Claudeエージェントが信用情報と計算結果を使い、日次サマリーと目玉オファーの選定理由を作成する。
- 比較対象時点、選定基準、参照元を記録する。

未確定：目玉オファーの選定基準、「変更」とみなす差分の閾値、出力形式。

## Phase 2：ファンド別のポートフォリオ入れ替え提案

### B1 ファンド戦略・制約条件の読込 ［構想］

- ファンド別の戦略と制約を共通形式にする。
- 通貨配分、為替ヘッジ、年限、デュレーション、格付け、信用リスク枠、集中制限などを扱う。
- 単位、適用日、版、必須項目を検証する。

未確定：設定ファイルの形式、項目の一覧と単位、版管理の方法。

### B2 ポートフォリオ入れ替え提案 ［構想］

Aladdin APIから現在の債券ポートフォリオを取得し、B1の戦略・制約、保有債券、現金、為替ヘッジ、
オファー（A1）、売却可能価格、取引費用などを使って、売りと買いを組み合わせた入れ替え案を作る。

- 対象：円債と外貨債の間の入れ替え、国債間の入れ替え、短期化／長期化、国債からクレジット債への入れ替え
- 戦略・制約の例：通貨配分、ヘッジ方針、デュレーション、年限、格付け、発行体集中、流動性、
  信用リスク枠、投資可能商品、売買単位、現金制約、取引コスト（B1で読み込む）
- 入れ替え前後の比較：通貨配分、利回り・ASW、デュレーション・DV01、信用リスク、費用、制約への適合
- 金利シナリオ：クオンツが指定するカーブやモデルを入力とする。
  「信用スプレッドを一定とする」分析は一つのシナリオ条件として明記し、信用リスク枠の計測とは分けて扱う。

成果物：売却候補、購入候補、数量、改善効果、費用、制約判定、信用上の論点を含む入れ替え提案。

未確定：Aladdin APIのポートフォリオ取得仕様、最適化の目的関数、取引費用のモデル、
信用リスク枠の計測方法、シナリオの入力形式。

### B3 Aladdin APIによる発注 ［構想］

提案で終わらず、Aladdinの発注APIへ接続する。

- B2の提案から発注案を作成する。売却、購入、必要な為替取引を同じ入れ替え案件として管理する。
- ファンドマネジャー等の所定の承認を経た注文内容だけをAPIで送信する。
- 発注ID、受付結果、約定、一部約定、取消などの状態を取得する。
- 二重送信を防止し、片側だけ約定した場合を管理する。
- 承認と送信の履歴を残す。

APIの仕様、認証、権限、承認フローは後で提示される。エンドポイントを推測して実装しない。
承認を経ない送信、テスト環境以外での試験送信は行わない。

## C1 TRSターム条件の読解・JSON・FpML ［実装済み・FpMLの公式XSD検証は未設定］

各社のTRS確認書・ターム条件（PDF・HTML。公開URLまたはローカル・Box Drive のファイル）を、R が取得・記録し、
R から起動した Claude Code が指示書（`docs/c1_trs_extraction_instructions.md`）に従って原資料を直接読み、
根拠（ページ・引用）つきの条件 JSON と FpML を作る。R が検証・保存・表示する（R → Claude Code → R。PowerShell は OCR の補助だけ）。
TRSの価格計算はしない。詳細は `R/c1_trs_terms/README.md`。

- 値の状態（記載あり／空欄／選択肢／記載なし）を区別し、推測で埋めない
- 記載ありの値には原文の引用が必要。引用が指定ページに実在するかを R が確かめる（AIの作り話・ページの誤りを検出）
- FpML の値は、レッグと番号ごとに条件 JSON と比べる（別レッグの値・部分一致では合格にしない。対応できない項目は未検証）
- 正式なFpML（fpml_final.xml）は、XML構文・公式XSD・原文根拠・条件との整合がすべて合格し、必須項目がそろったときだけ。それ以外はドラフト
- 公開サンプル（SEC の確認書）で実読解を試験済み
- 今後：同じ資料での複数回実行の揺れの測定、正解つき試験PDFでの正答率、Aladdin への送信
